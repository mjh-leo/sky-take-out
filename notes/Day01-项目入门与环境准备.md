## 四、前端环境 - Nginx 反向代理

Nginx 是高性能的 HTTP 和反向代理服务器。苍穹外卖项目前端打包后部署在 Nginx 上，API 请求通过反向代理转发到后端。

**为什么用反向代理？**
- **解决跨域**：前端（80端口）和后端（8080端口）不同源，浏览器有同源策略限制，Nginx 统一入口后不存在跨域
- **静态资源服务**：HTML/CSS/JS 由 Nginx 直接提供，速度快
- **统一入口**：前端只需要访问一个地址，不用关心后端具体端口,保证后端服务安全
- **负载均衡**：后端多实例时可以分发请求

**配置示例：**
```nginx
server {
    listen 80;
    server_name localhost;
     # 反向代理,处理管理端发送的请求
    location /api/ {
		proxy_pass   http://localhost:8080/admin/;
        #proxy_pass   http://webservers/admin/;
    }
}

upstream webservers{
	server 192.168.1.101:8080 weight = 90;
	server 192.168.1.102:8080 weight = 10;
}
```
**说明**：upstream 定义服务器组，proxy_pass 指定转发目标，配合使用实习反向代理与负载均衡。
负载均衡策略：轮询和weight权重等
**思考**：当前前后端分离开发成为主流，Nginx 反向代理几乎是标配。更现代的做法是用 API 网关（我所知如 Spring Cloud Gateway）统一管理鉴权、限流、路由，但小项目用 Nginx 足够。

## 五、后端项目结构（Maven 多模块）

苍穹外卖是一个 Maven 多模块项目，父工程聚合子模块：

| 模块           | 说明                                        |
| ------------ | ----------------------------------------- |
| sky-take-out | Maven 父工程，统一管理依赖版本，聚合其他子模块                |
| sky-common   | 子模块，公共类：常量类、工具类、异常类等                      |
| sky-pojo     | 子模块，实体类、DTO、VO 等                          |
| sky-server   | 子模块，后端服务：配置文件、Controller、Service、Mapper 等 |

**为什么要分模块？**
- 职责清晰：公共代码和业务代码分离
- 复用方便：common 和 pojo 可以被其他项目引用
- 编译加速：只改了 server 模块，不用重新编译全部

## 六、Entity / DTO / VO / POJO 区别

sky-pojo 模块中存放的是数据对象，四类对象各有用途：

| 类型     | 全称                    | 用途                             | 特点           |
| ------ | --------------------- | ------------------------------ | ------------ |
| Entity | 实体类                   | 和数据库表一一对应                      | 字段 = 表字段     |
| DTO    | Data Transfer Object  | 各层之间传递数据（如接收前端请求参数）            | 字段 = 接口入参    |
| VO     | View Object           | 为前端展示数据提供的对象                   | 字段 = 前端需要展示的 |
| POJO   | Plain Old Java Object | 普通 Java 对象，只有属性和 getter/setter | 最基础的对象       |

**理解：**
- 数据库有 `employee` 表 → 对应 `Employee` Entity
- 登录接口接收 `username` + `password` → 对应 `EmployeeLoginDTO`
- 登录成功返回 `id` + `name` + `token` → 对应 `EmployeeLoginVO`
- 它们都是 POJO（有属性有 getter/setter）
## 七、Git 版本控制

项目使用 Git 进行代码版本控制，基本流程：
1. 创建 Git 本地仓库（`git init`）
2. 创建 Git 远程仓库（GitHub/Gitee）
3. 将本地文件推送到远程仓库

**常用命令：**
```bash
git init                    # 初始化本地仓库
git add .                   # 添加所有文件到暂存区
git commit -m "init"        # 提交到本地仓库
git remote add origin <url> # 关联远程仓库
git push -u origin master   # 推送到远程
```

**思考**：公司里实际用的是**分支协作**：每个人在自己的分支开发，提 Merge Request / Pull Request，代码审查后合并到主分支。常用的分支策略有 Git Flow、GitHub Flow。后面可以单独学一下，毕竟涉及到协作，犯错的代价太高了。
## 八、登录功能完善 - MD5 加密

登录功能中，密码不存明文，用 MD5 加密后存储和比对。
**流程：**
1. 注册/新增员工时：密码 → MD5 加密 → 存入数据库
2. 登录时：用户输入密码 → MD5 加密 → 和数据库中的密文比对
**代码示例：**
```java
// Spring 提供的工具类
String md5Password = DigestUtils.md5DigestAsHex(password.getBytes());
```
**MD5 的特点：**
- 不可逆：不能从密文反推出明文
- 确定性：相同输入永远得到相同输出
- 固定长度：无论输入多长，输出都是 32 位十六进制字符串
**思考**：MD5 已经**不安全**了！相同密码加密结果相同，容易被彩虹表破解。生产环境推荐用 **BCrypt**（每次加密结果不同，自带盐值）或 **Argon2**。

## ⚠️ 避坑 Tips

### 1. 需求阶段的坑
- **需求没搞清楚就写代码 = 最快的慢**。返工成本是写代码的 5-10 倍，动笔前先问 3 个问题：给谁用？解决什么问题？什么算"做完了"？
### 2. 环境的坑
- **"在我电脑上能跑"是程序员三大谎言之一**。JDK 版本、依赖版本、配置文件任何一个不一致都可能导致线上崩。解决办法：统一用 Docker容器 或环境配置文档。
- 永远不要在生产环境直接改代码调试。生产环境的任何操作都要有备份、有回滚方案。
### 3. Nginx 反向代理的坑
- 启动nginx文件夹一定要放在英文目录下，放在中文目录下启动可能无效。
### 4. 项目分层的坑
- **Entity 直接返回给前端 = 泄露数据库结构**。数据库字段名、有哪些字段都暴露了，而且可能包含敏感字段（如 password）。一定要用 VO 封装后再返回。
- **DTO 和 Entity 字段大量重复**是正常的，不要偷懒用 Entity 接收请求参数，否则前端多传一个字段可能会直接写到数据库。
### 5. Git 的坑
- **不要把 `.idea/`、`target/`、`.iml` 提交到 Git**，一定要配 `.gitignore`。
- **commit message 要写清楚**，别写"更新""修改"这种没用的信息，写清楚改了什么功能。
- **push 前先 pull**，避免覆盖别人的代码。

## 🎯 面试题
### Q1：你们项目的开发流程是怎样的？

 1 需求阶段：产品经理出原型，我们开需求评审会，确认功能范围
 2 设计阶段：架构师定技术方案，我负责数据库设计和接口定义
 3 开发阶段：按模块分工，我负责 XX 模块，写代码 + 单元测试
 4 联调测试：前后端联调，提测后测试工程师找 bug，我负责修复
 5 上线：运维部署，我配合验证线上功能
 
 重点：**说清楚每个阶段具体做了什么**
### Q2：开发、测试、生产环境有什么区别？为什么要隔离？

- **隔离原因**：防止开发中的 bug 影响真实用户，防止测试数据污染生产数据，防止未完成的功能被用户看到。
- **开发环境**：随便改，怎么折腾都行
- **测试环境**：尽量模拟生产，但数据是假的
- **生产环境**：真实用户在用，任何改动都要谨慎，要有回滚方案
### Q3：Entity、DTO、VO、POJO 有什么区别？

> **一句话记住**：Entity 对数据库，DTO 对接口入参，VO 对前端展示，POJO 是它们的统称。

- **Entity**：和数据库表一一对应，字段 = 表字段
- **DTO**：数据传输对象，用于接收前端请求参数或层间传递数据
- **VO**：视图对象，返回给前端展示用的，只包含前端需要的字段
- **POJO**：普通 Java 对象，只有属性和 getter/setter，是前三者的基础形态

> **面试话术**："我们项目里严格分层，接收请求用 DTO，数据库操作用 Entity，返回前端用 VO，不会把 Entity 直接返回给前端，因为会泄露表结构和敏感字段。"
### Q4：什么是跨域？怎么解决？

- **跨域原因**：浏览器的同源策略，协议、域名、端口任一不同就会跨域
- **解决方案**：
  1. **Nginx 反向代理**（本项目用的）：前端和接口都走 Nginx，同源了
  2. **CORS**：后端设置响应头 `Access-Control-Allow-Origin`
  3. **JSONP**：只支持 GET，过时了
  4. **前端代理**：开发环境用 webpack/vite 的 proxy 配置

> **面试话术**："我们项目生产环境用 Nginx 反向代理解决跨域，开发环境用 Vite 的 proxy 配置。原理都是让前端和接口看起来同源。"
### Q5：Maven 多模块项目有什么好处？

- **职责分离**：公共代码（common）、数据模型（pojo）、业务逻辑（server）分开
- **复用性**：common 和 pojo 可以被其他项目引用
- **编译效率**：只改了业务代码，不用重新编译公共模块
- **团队协作**：不同人可以负责不同模块，互不干扰
### Q6：你们团队的 Git 协作流程是怎样的？

> **参考回答**：
> "我们用的是 GitHub Flow 风格：主分支是 master，每个人开发新功能时从 master 拉一个 feature 分支，开发完后提 Pull Request，代码审查通过后合并到 master，然后自动部署。
> 常用命令：git checkout -b feature/xxx、git add、git commit、git push、git pull --rebase。
> 我知道还有 Git Flow（有 develop、release 分支），但互联网公司更常用简单的 GitHub Flow。"
