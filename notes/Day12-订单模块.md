# Day12 - 订单模块

## 一、订单搜索

### 1. 业务流程

1. PageHelper 分页查订单
2. 遍历每条订单：
   - BeanUtils 拷贝到 OrderVO
   - 根据订单 id 查菜品明细 order_detail
   - stream 把明细拼成 `菜名*数量;` 每个菜拼成字符串
   - 设置到 VO 的 orderDishes 字段
1. 封装 PageResult 返回
### 2. 为什么要把明细拼成字符串？

看原型设计才知道：**部分状态的列表页要展示菜品信息**，格式是"菜名*数量"，比如：

```
鱼香肉丝*2; 宫保鸡丁*1;
```

**为什么不是返回 List？** 因为列表页只需要一列展示，前端不想再嵌套循环，直接给个拼好的字符串，一行搞定。这是**前后端约定**的展示格式。

```java
String orderDishes = orderDetailList.stream()
        .map(d -> d.getName() + "*" + d.getNumber() + ";")
        .collect(Collectors.joining());
```

> **思考：** 不要觉得"拼字符串"简单。接口怎么返回，是看前端怎么用。列表页只要一行文案，返回 List 反而让前端多做一步拼接。**接口设计要服务前端的使用方式**。

## 三、查询订单详情（重点：水平越权）

### 1. 复用代码

小程序端写过订单详情查询，后台管理端逻辑基本一样，直接复用之前的业务代码，只新增接口。

### 2. 但发现了一个安全问题：水平越权！

```java
Long loginUserId = BaseContext.getCurrentId();
if (!orders.getUserId().equals(loginUserId)) {
    throw new OrderBusinessException("无权查看该订单");
}
```

**什么是水平越权？**

> 用户 A 只能操作自己的数据，但通过**修改参数（比如订单 id）**，能访问到用户 B 的数据。

**场景：** 用户 B 的订单 id 是 10086。用户 A 抓包，把请求里的订单 id 改成 10086，如果后端不做校验，A 就能看到 B 的订单信息——包括地址、手机号、买了什么。

**怎么防：** 查询时校验订单的 user_id 是不是当前登录用户。不是就报"无权查看"。

**两类越权：**

| 类型 | 是什么 | 例子 |
|------|--------|------|
| 水平越权 | 同级别用户互访数据 | A 用户看 B 用户的订单 |
| 垂直越权 | 低权限用户访问高权限功能 | 普通用户调用管理员接口 |

## 四、接单、拒单、取消订单、派送订单、完成订单

接单比较简单：商家把"待接单"订单改成"已接单"。
### 1. 订单状态机

订单的整个生命周期：

```
待付款 → 待接单 → 已接单 → 派送中 → 已完成
   ↓         ↓
  已取消    已取消（拒单）
```

每个状态只能做规定的操作，**状态必须按顺序流转，不能跳步**。

### 2. 拒单业务流程

```java
public void rejection(OrdersRejectionDTO dto) {
    Orders orders = orderMapper.getById(dto.getId());
    
    // 1. 只有"待接单"状态才能拒单
    if (orders == null || !Orders.TO_BE_CONFIRMED.equals(orders.getStatus())) {
        throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);
    }
    
    Orders update = new Orders();
    // 2. 用户已支付的话，要退款
    if (Orders.PAID.equals(orders.getPayStatus())) {
        update.setPayStatus(Orders.REFUND);
    }
    // 3. 状态改为已取消，记录原因和时间
    update.setId(orders.getId());
    update.setStatus(Orders.CANCELLED);
    update.setRejectionReason(dto.getRejectionReason());
    update.setCancelTime(LocalDateTime.now());
    orderMapper.update(update);
}
```

**关键点：**
- **先查状态再操作**：只有待接单能拒单，别的状态拒单要报错
- **已支付要退款**：不能用户付了钱，你拒单却不退钱
- **记录原因和时间**：拒单要写原因，方便追溯

## ⚠️ 避坑 Tips

### 1. 水平越权的坑
- **所有查询接口都要校验数据归属**。只要接口通过 id 查数据，就要校验这个数据是不是当前用户的
- **不要只靠前端隐藏入口防越权**。前端只是不显示按钮，抓包一样能调接口，后端必须校验
- **商品、地址、订单、购物车，所有按 id 查询的接口都要防**。不是只有订单
- **越权分水平和垂直**。水平是同级别互访，垂直是低权限访问高权限功能，两个都要防
### 2. 订单状态机的坑
- **每个状态操作前都要校验当前状态**。只有待接单能拒单、只有派送中能完成……状态不对就抛异常
- **状态流转要闭环**。拒单要退款、取消要记录原因、完成要记录完成时间，每一步都有配套动作
- **并发下单的状态变更要小心**。两个操作同时改一个订单，可能状态错乱，重要场景要加锁

## 🎯 面试高频题

### Q1：什么是水平越权？怎么防？

> **回答框架：**
> 1. **是什么**：用户 A 通过修改参数（比如 id），访问到用户 B 的数据
> 2. **场景**：订单详情接口，抓包改订单 id，就能看别人的订单（地址、手机号都泄露了）
> 3. **怎么防**：查询时校验数据归属——`orders.getUserId().equals(BaseContext.getCurrentId())`，不是自己的就报错
> 4. **延伸**：垂直越权是低权限用户调高权限接口，用权限框架（如 Spring Security）控制
> 5. **项目里**：订单详情加了数据权限校验，防止水平越权
>
> **面试话术**："我在项目里遇到过越权问题。用户端订单详情接口，如果只按订单 id 查不校验归属，别人抓包改 id 就能看你的订单。我加了校验：查询后判断订单的 userId 是否等于当前登录用户，不等就抛'无权查看'。"

### Q2：订单状态怎么设计？为什么每个操作要校验状态？

> **回答框架：**
> 1. **状态机**：待付款 → 待接单 → 已接单 → 派送中 → 已完成，还有分支：已取消
> 2. **为什么校验**：状态必须按顺序流转。待接单才能拒单、已接单才能派送、派送中才能完成。不然用户下单 5 分钟，商家直接点"已完成"，状态就乱了
> 3. **配套动作**：拒单要退款、取消要记录原因、完成要记录时间
> 4. **实现**：操作前先查订单状态，不匹配抛业务异常
